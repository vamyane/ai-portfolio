# 小红书评论工作台 · 代码模块规范（v1，2026-09-02）

> **目的**：杜绝"改 A 功能把 B 功能改坏"。本文件是开发的**强制约束**——每个文件属于哪个模块、能改什么、不能碰什么，动手前先看这里。

## 🚫 最高铁律（违反 = 事故）

1. **改功能 = 只改该功能自己的模块文件**。判断归属 → 只动它 → 结束。
2. **要动其他模块的文件/接口 = 先停下来问用户**（改什么、为什么影响它、怎么改），用户拍板才动手。
3. **新功能 = 新建独立文件**，禁止塞进现有模块。
4. 打包/安装涉及替换 workbench 目录——**先确认当前源码状态干净**（如曾发生 0.2.11 解包误装覆盖 0.2.18 的事故）。

## 🔁 开发流程（每次改动走一遍）

```
① 用户提需求 → 判断属于哪个模块（查上表）
② 只属于一个模块 → 只改该模块文件
③ 涉及多个模块/公共文件（index.html 主 JS、engine.js、server.js）→
   列出方案：改什么 / 会碰哪些模块 / 影响什么 → 问用户确认
④ 新增功能 → 新建 web/modules/xx.js 或 core/xx.js（+ server 路由若需要）→ 主文件只加调用
⑤ 改完 → node --check 语法 → 相关模块单测 → 再打包
```

## 📌 检查清单（改动后自问）
- [ ] 我动的文件都属于目标功能模块吗？
- [ ] 有没有"顺手"改了无关文件？（有 → 撤销）
- [ ] 有没有改变其他模块的行为/默认值？（有 → 告诉用户）
- [ ] 新功能是不是塞进旧文件了？（是 → 拆出去新建文件）
- [ ] 历史用户认可的行为（默认词库 0.2.11 策略等）被动了吗？（动了 → 为什么？用户同意了吗？）
